# V-bar与末端视觉抓取的交接约定

更新：2026-10-30，核对main `3562567`及本分支。**已具备状态继承接口，尚未接通目标星自动调姿及near23自动抓取。** 不需要重写整套交会，但不能把独立抓取场景的初态直接套到正式停泊点。

## 两部分分别负责什么

V-bar负责服务星整个平台怎么接近、在哪里停、是否允许继续；视觉负责测出目标在哪里、朝向如何；机械臂负责在平台停稳后移动夹爪、接触、闭爪和保持力。V-bar是一条随目标轨道转动的接近线，不是一种传感器。

| 时机 | 你的输入或输出 | 接收方和处理 |
| --- | --- | --- |
| 尚未识别靶标 | 输出无有效视觉，不编造位置 | 导航继续使用GNSS；V-bar按选定任务规则决定等待或续行 |
| 候选17.4 m停泊完成后预对准 | 接收同历元GNSS相对位置/速度、服务星姿态/角速度、机械臂编码器、目标星合作姿态/角速度 | `EndStereoGeometry`计算面对相机的姿态参考，`PrealignmentController`计算目标力矩；实际目标执行器/控制权待正式集成 |
| 图像有效后，每个新曝光历元 | 输出坐标换算后的相对位置、时间、协方差和质量；保留会话/原图帧号 | 正式导航在曝光历元修正，再预测到当前时刻；视觉就绪与V-bar节点放行另行判断 |
| 平台到站并允许机械臂工作 | 接收已校验的 `NearParked`交接、实际关节/导航/传感器状态 | 保留原物理状态，机械臂先从收拢构型展开并对准，不重摆两星初态 |
| 末端接近及短暂缺图 | 输出机构中心在夹爪系的位置/朝向；缺图由陀螺＋编码器补偿自身运动 | 原预测抓取控制器接近；异常或预算超限停止，接触后切换原闭爪/力控 |

`R,t`描述目标本体系到相机系的变换。机构参考点先算 `c_C = R c_T + t`，再通过静态安装外参到夹爪；交给导航则还需曝光时刻机械臂FK和服务星姿态。位置协方差需包含角点、标定、姿态和编码器误差，不能把重投影px直接当m²。

`ImageRelativeNavigation`目前输出的是 **J2000系、目标本体原点减服务星本体原点** 的位置测量，面向旧 `near_field.RelativeEKF`。最新capture26用双星COM状态的 `PoseNavigation`及完整位姿/协方差图像协议；两者不是同一个数据包。接入需补齐本体原点→装配COM的杆臂及转动/关节速度、曝光时刻变换和协方差，不能仅重命名字段后塞入。已有 `origin_lever_arm.py`、`assembly_geometry.py`可复用相关计算。

## 主线已有的交接

`mission_runtime.handoff`读取并校验完成的 `NearParked`，创建同模型操作场景。`teleop_grasp_unreal`检测到capture26交接后，转入 `capture26_operations.run_scene`，继而进入 `capture26_runtime.run`。

该运行时继承完整物理快照、两臂/轮系状态、GNSS接收机与在途包、双星导航、陀螺历史、环境和控制参考。接收端继续保持同一个作业参考并按平台状态开放操作臂。**这一段是现成接口，不是本次新增的自动抓取成功证据。** 本轮未获得一份实际飞行生成的合格NearParked记录来执行near23连续交接。

## 当前不能直接接上的差别

1. **运行入口不同。** 独立near23场景通过 `randomization.capture_window_trial`和 `capture_visual_test`安装自动控制器。正式operations分支没有消费这份配置，仍创建普通 `Capture26Component`。工具现在会拒绝向带交接的场景写入这项不生效的配置，防止误报启用。
2. **“0.5 m”初态不同。** 主线参考是收拢TCP到实际表面的轴向间隙0.5 m，另外带目标系 `[0,0,1.25] m`侧向偏移。它不是视频里夹爪已对准接口的0.5 m起点。必须从实际关节状态规划展开、朝向、避障和视觉获取；离线位置IK成功也不能替代整段动作验收。
3. **参考点不同。** V-bar使用目标表面 `[0.1755,0.08325,0.04207870013] m`；本版视觉抓取使用 `[0.1755,0.05475,0.04207870013] m`。Y相差28.5 mm，是不同几何定义，应显式换算并与接触控制约定一致，不能当测量偏差减掉。
4. **目标星姿控不同。** 主线目标星被动演化；本周调姿施加受限等效力矩，末端预测器在接触前假设目标保持。需要统一控制权和模式切换，避免两套控制同时施加力矩；目标自由转动也不能当作“保持目标”盲抓。
5. **相机和导航定义不同。** 主线导航使用本体系固定相机及自己的标定ID；near23在夹爪上，会随机械臂运动。要分别保留标定、会话、曝光和编码器历史；不能用near23配置覆盖已有交接的导航标定。

当前 `config/missions/capture26-v2.json`默认 `simulation_state_demo_v1`，控制反馈来自仿真真值，视觉健康不阻止四节点运动。另一严格图像路线有4 m获取/2 m就绪配置，但尚未统一认证。旧通用 `near_field`路线的12 m保护也仍保留。本次没有把这些路线改成自动17.4 m调姿或纯GNSS近距放行。

## 可复查入口与下一次运行

```powershell
# 静态核对当前版本的机位、标定、参考点和未接通项；不启动/改写仿真。
python tools/diagnostics/inspect_vbar_near23_handoff.py --output run/vbar_contract_new.json

# 有正式任务实际产生的交接后，先使用原校验器检查，再生成同样的接口报告。
python tools/diagnostics/inspect_vbar_near23_handoff.py --handoff <实际NearParked文件> --output run/vbar_contract_actual.json
```

静态报告中的 `automatic_capture_connected=false`不会因提供交接文件变成true。成功读取交接只证明已有交接校验通过，不是抓取许可；旧阶段、错误标定、丢失历史、非NearParked等输入会失败。

下一次集成应在正式运行时加一个明确选择的模式，依次执行：17.4 m停泊后预对准并持续稳姿→真实图像质量合格后按新约定继续→实际NearParked状态继承→收拢臂展开与接口对准→启动near23预测抓取→逐物理步验收接触与保持力。需要同时记录导航对真值误差、节点位置/速度/驻留、姿态跟踪、双眼有效性和连续抓持，不能拼接独立试验作为整条任务通过。
