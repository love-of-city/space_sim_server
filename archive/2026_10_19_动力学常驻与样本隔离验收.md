# 动力学常驻与样本隔离验收

## 实现边界

批量入口支持 `reuse_dynamics`：每路独立持有一个 Python 动力学进程，串行处理本路请求。每条仍重建 BSK 图、MuJoCo 运行状态、任务、轨道/姿态组件、控制器、随机数流、观测延迟队列、通信和录制会话。仅解释器、导入库和原生库加载结果可以跨条保留，不复用上一条的物理积分状态，不跳过 `InitializeSimulation`。

仓库 `space_sim_server/config/collection.json` 开启此模式；历史配置未提供开关时仍默认关闭。`dynamics_max_episodes=4`、`dynamics_max_rss_mb=8192` 限制条间复用：达到任一阈值后完整结束当前条，再退出 worker；下一条自动创建新进程。RSS 单位为 MiB，是清理后的阈值，不限制单条运行中峰值。原生图/分配器的长期内存释放尚未证明稳定，因此不允许无限复用。

每条请求有独立 ID，进程身份通过 PID、创建时间和 token 核对；同一 mailbox 不允许两个未完成请求。结果在清理后发布，拒绝过期响应。任务失败、未知残留线程使该进程退出；基础设施故障停止批次。取消文件按条隔离，父采集器消失时 worker 退出。Windows venv launcher 与实际解释器 PID 不同的情况也单独处理。

首次实机测试发现 Basilisk 即使关闭进度显示，也会由 tqdm 创建全局 TMonitor；因此在专用常驻入口设置 `tqdm.monitor_interval=0`。未放宽通信线程泄漏检查。

## Linux 4090 真实录制

环境：原有 Linux 4090、UE 5.6.1、BSK/MuJoCo、双相机 1024×1024 / 50 Hz、腕力 200 Hz。沿用当前含六项噪声和在轨位置随机的场景，不降低采样率或修改视频编码。

证据目录：`/home/spacesim-zmh/migration/persistent-dynamics-acceptance-20261019/`。`validation.json` 记录完整验收，`sensor-independence.json` 记录传感器数值比较。诊断失败另保存在 `persistent-dynamics-validation-20261019-233338` 和 `persistent-dynamics-diagnose-20261019`，未覆盖失败证据。

先以独立进程录制冷启动 A，再在同一动力学进程中执行 A→B→A；A/B 种子分别为 202610198000 / 202610198001。四条均完成真实任务、双视频完整解码、相机与状态逐帧配对和 LeRobot 数据验收。复用进程 PID 91207，完成计数依次 1、2、3，清理后均无额外 Python 线程。

- A 的初始 qpos/qvel、轨道、任务事件和任务完成时间在冷启动、常驻首条及 B 之后一致。
- 四条 episode ID 和 render session ID 各不相同，每条内部只有本条的会话 ID。
- 每条动力学初始时间为 0；抽屉任务实际第一条录制观测为 20 ms，不能误要求首帧为 0。
- 比较共同仿真时刻的观测和动作；冷启动 A 与两次常驻 A 各比较 1,753 帧观测和 7,009 条 200 Hz 腕力采样。关节位置、速度、动作、腕力/力矩及力传感真值的最大绝对差均为 0；测量时间与关节真值也完全一致。
- STOP 是成功后的异步握手，允许末尾成功保持帧数量不同。所有额外帧都在任务成功后；不放宽任务阶段、帧连续性或相机配对验收。

## 自动与批量验证

Windows 与 Linux 各 50 项相关测试通过：worker 请求隔离、取消、异常、残留线程、异常死亡、条数/RSS 回收、协调器并发与失败清理、配置传递、噪声及轨道随机化。相关 Python Ruff 检查通过。此前录制/紧凑格式/任务回归 38 项通过；这不是全仓库 CI 或所有任务的原生复用验收。

生产批量入口使用另一个独立验证目录 `persistent-dynamics-batch-20261019`，将回收间隔设为 2 条。3 次尝试得到 3 条完整验收成功的数据，前两条动力学 PID 为 93359，第二条返回 `retirement_reasons=["episode_limit"]`；第三条自动创建 PID 94491。协调器最终 `status=complete`，总耗时 269.924 秒，短批次吞吐 40.011 条/小时；不能作为长期吞吐预测。协调器、UE、两个动力学进程均已退出。

三条的启动时间分别为 29.35、26.95、29.51 秒；前两条完成录制与验收分别耗时 81.47、76.15 秒，第三条为 105.58 秒。种子不同，任务长度和运行时长也不同，因此不能直接用这三个总耗时估计加速比例。结果以该目录 `run/summary.json` 为准。

已有两个 50 条数据集及 H800 副本不作更改。此次验证数据位于 migration 验收目录，没有混入训练数据集。
