# 仿真与采集验证缺口

核对日期：2026-10-31；源码基线 `30dea8f`。本页区分已有机制、尚缺的统一标准和需要补做的验证，供[任务对齐](../guides/simulation-data-workflow.md)使用。下表的角色是建议负责职责，尚未指定个人；补齐条件是后续工作要求，不表示代码已自动执行，也不新增默认采集门禁。

## 除参数文档之外还需要补齐什么

| 性能与长稳 / 中 | 有RTF、初始化、图复用、审核和批次墙钟；当前五任务验收不足以给稳定小时产出 | 固定硬件/输入/任务分布，保存完整审核后的通过条数、所有失败和总墙钟，记录内存/显存趋势与回收；8小时/100尝试是此前工程方案的待执行范围，不是已通过结果 | 采集、工程 |
| UE早期启动崩溃 / 中 | 先前并行构建/验证时出现SIGSEGV；独占五任务和启动对照未复现，根因未定位 | 保留崩溃来源、负载和日志；受控复现、定位及回归。不能把“本次未复现”登记为修复 | UE、工程 |
| 环境/跨平台重建 / 中 | 有来源门禁和重建工具；Windows实机、完整隔离Python重装、跨机完整任务未认证 | 固定依赖解析结果及哈希，干净环境重建，再完成适用native/UE/GPU/完整任务；对具体平台分别给结论 | 发布、工程 |
| CI执行与维护 / 中 | 已有分层workflow和策略文件，远端受控runner/分支保护配置未完成 | 对实际远端配置和运行结果给证据；检查名存在不能代替执行通过 | 工程维护 |

“高”表示下一次声明训练合格或更改正式采集行为前优先对齐；不是要求本次文档工作自动启动长稳、修改成功阈值或重审旧批次。

## 已发现的文档歧义及本次处理

| 歧义 | 现在如何读取 |
|---|---|
| 历史v15插头完成说明与当前控制器版本混在同一长文 | 当前任务版本和阈值集中到[任务与数据验收](task-and-data-acceptance.md)，旧日期段落保留历史适用范围 |
| 看到MJCF/旧scenario步长就当作正式执行步长 | [物理配置](physics-model-configuration.md)按加载顺序说明运行覆盖，配置声明和实际积分分开 |
| 所有入口都“自动时间seed”或“第二条只reset” | [采集配置](collection-configuration.md)逐入口标默认；图兼容、worker存活和任务模型条件共同决定复用 |
| `accepted`、目录名、任务成功和训练资格混用 | 分清attempt/序列/审核层级和`full_validation_pending`；训练资格另做审查 |
| 录制配置被称作完整快照 | 明确现有机制包含路径和哈希，需保留外部原件及完整依赖 |
| 旧30 Hz GPU回放诊断被当成当前50 Hz动力学采集验收 | 验证器按入口、平台、输入和覆盖范围说明，不凭脚本名称授予认证 |
| 主目录已完成验收但导航仍说仅候选工作树验证；旧批次状态易与后续新批次混淆 | 更新入口说明，指向主目录验收证据、带日期的旧批次停止记录及各批次实时状态入口 |

## 如何关闭一个缺口

在仓库外对应报告中记录：问题ID/描述、受影响版本和任务、已约定标准、输入哈希、实际命令/环境、通过与失败证据、未覆盖项、结论及日期。修改实现时更新相应版本和参考文档；纯补充审核结果不改原始录制来源。

已有证据入口为本机 `reports/ue-engineering-implementation-20261031/REPORT.md`，完整录制结果为同目录 `recording-acceptance.json`，实际录制输出在 `artifacts/verification/ue-engineering-20261031/five-task-capture-main/`。这些是仓库外证据，其他机器需要另行取得；文档链接不能替代原始文件。
