# SpaceSim Linux 迁移方案（环境实查版）

日期：2026-10-19（Asia/Shanghai）。目标主机：117.50.205.199:22；运行用户：spacesim-zmh。
本次仅检查环境并设计方案，未安装软件、上传项目、修改远端服务或启动采集。本文不保存密码。

后续范围调整：用户要求先完成基本迁移，不考虑千条数据容量。实施使用现有磁盘，暂不扩容；下文 300–500 GB 只是长期部署预算建议，不是基础迁移前提。适配工作在独立的 `space_sim_linux_migration` 工作区推进，实际进展以其中 `space_sim_server/docs/LINUX_BASIC_MIGRATION.md` 和验收记录为准。

## 1. 结论与范围

目标机具备部署完整 SpaceSim 单路采集的硬件基础：已识别 RTX 4090，CPU、内存可用于动力学和软件视频编码。但 UE/Vulkan 尚未验收，代码存在 Windows 原生运行库及启动器依赖，不能直接复制 Windows 环境后运行。

建议先在 Linux 本机跑通动力学、UE、采集全过程，再迁移网页和公网访问。以现有完整采集结果为对照，保留 BSK 轨道物理、原生几何加速、流式视频和 compact 数据格式。迁移完成后再单独评估 NVENC、实例预热和并发；不以降低采样率、关闭 BSK 或丢帧达到倍率指标。

## 3. 版本与迁移内容

当前 Windows 工作区基于 commit `2c8637e3c22bbc0eb2b70bff99335d65abfac4ed`，分支 `feature/bsk-orbital-environment-j2`。检查时有 322 个 Git 状态条目，包含已修改 UE 资产、动力学配置、未跟踪的新模块和测试。不能只克隆该 commit 并宣称与当前运行代码一致。

实施时先建立可复现的源码/资产快照：

1. 记录基线 commit、工作区差异、需纳入的新增文件和各文件 SHA256；覆盖已验证的 compact_storage、recording_config、streaming_video 等文件。
2. 核对 Git LFS 资产为真实内容而非指针，并纳入当前修改的 UE 资产。按明确清单导出；不能只依靠 git diff，后者遗漏未跟踪文件。
3. 同步源码、模型、必要 UE Content/ContentSource、配置和构建说明。在 Linux 复核清单与校验和。
4. 排除 Windows .venv、DLL、UE Binaries/Intermediate/Saved、日志、录制数据、临时缓存、凭据和本机生成的绝对路径目录映射；在 Linux 重建这些运行产物。生成资产以所需 Content 文件为准，不能泛化为全部删除。
5. 核对模型、相机、材质和插件引用的大小写；场景绝对路径和资产 catalog 在目标机重新生成。

当前受 Git 跟踪文件的工作区大小约 0.95 GiB（含模型和 UE 资产，不含 .git、未跟踪文件和引擎），最终传输大小以冻结清单为准，无需整体复制 Windows 工程目录。

## 4. 存储与目录安排

建议增加 300–500 GB SSD 数据盘作为初始开发/部署容量规划；这是预算建议，不是已测得的 UE 最小需求。若编译完整引擎源码，应重新估算源码、编译中间产物、DDC 和并行构建峰值，可能需要更大空间。批量数据另按保留策略扩容。

确认新盘实际挂载后再使用 `/data`，避免误写系统盘。建议布局：

```text
/home/spacesim-zmh/src/space_sim_server/  源码和可审核配置
/data/spacesim-zmh/engines/UE_5.6/       Linux 引擎
/data/spacesim-zmh/envs/                Python 环境
/data/spacesim-zmh/cache/               下载、构建、UE DDC 缓存
/data/spacesim-zmh/runtime/             场景、进程记录、日志
/data/spacesim-zmh/datasets/            验收通过的训练数据
/data/spacesim-zmh/validation/          独立验证和测速结果
```

上述业务目录由 spacesim-zmh 拥有，不修改其他用户目录。盘未准备前，可以推进小规模代码适配和依赖可用性检查，先不下载完整 UE。数据量按当前约 79.5 MiB/条的样例估算：1000 条约 77.6 GiB、10000 条约 776 GiB，尚未计日志、失败任务和其他场景差异。下载、构建和数采都应做剩余空间预检查。

## 5. 需要修改的代码

| 模块 | 当前限制 | 迁移实现 |
| --- | --- | --- |
| `native/local_mujoco_stepper.cpp` | 用 GetModuleHandleW/GetProcAddress 查找 Basilisk 的 MuJoCo，非 Windows 明确失败 | 增加 Linux 已加载库发现与符号解析；核验实际 ELF 依赖和符号归属，通过对应已加载句柄及 dlsym 调用同一运行库。不能再加载独立 pip MuJoCo 替代 |
| `simulation/local_mujoco_stepper.py` | 查找 mujoco.dll，接口使用 c_wchar_p | 增加 Linux 运行库查找和适配的路径接口；调整 ABI 时同步 Python/C++ 及构建 manifest，并拒绝旧不兼容产物 |
| `tools/build_native_acceleration.py` | 仅 MSVC，输出 DLL | 增加 GCC/Clang .so 构建；保留源码/库哈希、头文件和运行库版本校验。使用严格浮点策略，不开启 fast-math |
| `tools/build_sarm_plugin.py` | 使用 DLL/.lib/.def | 增加 Linux SDF 插件编译、运行库链接和搜索路径；确认插件注册在同一 MuJoCo 运行库，验证 SDF 数值和接触行为 |
| `tools/record_drawer_task.py` | 固定 Win64/UnrealEditor-Cmd.exe | 将 UE 目录、可执行文件及平台参数交给统一解析器；Linux 选择真实存在的 UE 可执行入口 |
| `backend/space_arm_platform/scene_runtime.py` | 调用 PowerShell 启停脚本 | 增加 Python/Linux 场景生命周期实现；保留 Windows 路径，通过平台选择统一接口 |
| `backend/space_arm_platform/collection_processes.py` | Windows Job Object；Linux 分支未实现等价进程回收 | 增加 Linux 进程组管理；服务/任务使用 systemd cgroup 管理崩溃后的回收，测试停止与异常路径。仅 killpg 不保证父进程崩溃后的自动回收 |
| UE 构建、资产准备和平台启动脚本 | 依赖 PowerShell、Windows 工具路径 | 增加 Linux 入口；可共享逻辑转为 Python，不靠安装 pwsh 掩盖 DLL/Win64 等依赖 |
| CI、说明和部署 | Windows 为主要完整入口 | 增加 Linux Python/构建检查、平台参数测试；GPU/UE 实机验收单独留证 |

BSK、MuJoCo 和模型 ABI 是优先技术验证项。当前本地版本为 Python 3.13.14、bsk 2.11.1、MuJoCo 头文件 3.7.0、numpy 2.3.5、lerobot 0.4.4、av 15.1.0、torch 2.10.0。Linux 优先匹配版本，但必须先验证 Linux 二进制包、MJScene API 和动态库布局；若需源码构建或选择另一 Python 小版本，应明确记录并重新验收，不默认升级 BSK。

## 6. 配置与数据格式

继续以 `space_sim_server/config/recording.json` 管理采集语义：双相机 1024×1024 RGB、50 Hz 仿真时间采样、400 Hz 动力学、200 Hz 控制反馈与腕力；保留 BSK、原生几何加速、2 ms 容量轮询、有限队列与严格完整性检查。

保持 compact 格式、关闭 cameras 原图副本和动力学调试轨迹。保留 LeRobot 数值数据、视频、元数据、相机上下文及高频腕力。先使用当前软件 H.264 流式编码（CRF 30、GOP 2、每相机 2 编码线程、队列 30 帧）。不从迁移中引入训练格式或采样语义变化。

建议新增独立机器配置文件（拟议接口，尚未实现），集中管理 Python/UE/模型/数据路径、监听地址、端口范围、GPU 选择和并发上限。录制配置与机器配置职责分开，任务 summary 同时记录有效采集配置和必要的环境版本。密码、访问令牌不进入配置模板或 Git。

NVENC 作为后续可选对照实验：当前只验证 libnvidia-encode 可加载，尚未验证目标 PyAV 编码器、实际编码和训练解码。相同 QP/CRF 数字不代表相同质量；速度、体积、画质、关键帧和完整解码全部通过后再决定是否切换。

## 7. 分阶段实施与通过条件

### A. 冻结基线、准备磁盘与依赖

形成源码/资产清单，建立目标目录；安装 Git LFS、Python 管理工具、编译依赖、Vulkan loader/工具及 UE 所需系统库。Node.js 22 用于后续完整平台。使用独立 Python 环境，不替换系统 Python；UE 使用与 5.6 相匹配的 Linux 工具链，不能直接把系统 GCC 当作 UE 完整构建环境。

通过条件：磁盘路径真实挂载、文件可写、依赖版本可记录；vulkaninfo 能识别 NVIDIA 实际 GPU 而非软件渲染器。图形设备权限按实际错误补齐，不预先开放全局设备权限或用 root 运行 UE。

### B. 先跑通真实动力学

安装匹配的 Basilisk；执行 scripts/check_basilisk.py；完成原生库及 SARM 插件 Linux 支持。运行模型加载、FK/Jacobian、BSK 引力/轨道、关节伺服、接触和腕力相关测试，以及完整无图像任务。

通过条件：使用真实 MJScene，所有原生组件 ABI 一致，任务阶段和终态正确，物理数值在预先确定的容差内。跨编译器不要求逐位一致；重点检查轨迹误差、接触事件、成功率与非有限值，不能以关闭物理组件掩盖问题。

### C. UE 双相机短采集

准备合法可用的 Linux UE 5.6 构建和工具链，编译 BskUnrealRuntime 及其 PixelStreaming2 依赖，重新生成 Linux 资产映射。用 Vulkan/offscreen 模式加载真实模型和相机；具体启动参数以所用引擎验证结果为准，不能使用禁用渲染的 NullRHI 来验收图像。

先执行 5–10 秒诊断采集：确认两相机中卫星和机械臂可见，姿态随动力学变化，帧号/时间戳连续且严格配对，排除只有调试文字或全黑画面。短诊断即便数据完整，也不作为成功任务训练样本。

### D. 完整任务与性能验收

同一模型、场景、随机种子、有效录制配置运行完整抽屉任务。记录启动、正式录制、收尾、校验和总耗时，分别计算 RTF；采集 CPU/GPU/内存/磁盘指标。建议至少重复 3 条，报告中位数和波动。

Windows 已验证参考：仿真记录跨度 128.36 秒；正式录制 171.64 秒（0.748×）；录制加收尾 182.47 秒（0.703×）；脚本总耗时 249.59 秒（约 0.514×）；独立数据验证另耗时 22.70 秒。参考样本有 6419 个状态/动作帧、12838 个相机图像帧和 25673 个腕力样本，约 79.5 MiB。跨平台末端帧数若有差异，应结合终止边界审计，不能仅以数目接近认定等价。

通过条件：完整任务成功，数值数据与相机逐帧对齐，视频完整解码，腕力连续、源哈希有效、官方 LeRobot 可加载采样，图像统计合理，无临时 PNG 堆积；取消、失败、重试时无孤儿进程或数据误标成功。性能先争取不退化，再以同一计时口径争取 1×；Linux 本身不保证提速。

### E. 完整平台与公网访问

完成后端、前端、信令、场景启停及后台采集管理迁移；以 systemd 服务的 User=spacesim-zmh 运行，配置任务 cgroup、日志轮转和明确的失败恢复。启动恢复先识别未完成 episode，不能静默追加或覆盖已验收数据。

先本机/API 验证，再验证远程浏览器：HTTPS 反向代理、WebSocket、WebRTC ICE/公网候选及必要的 TURN/UDP 路径。网页可打开不代表视频链路打通，WebRTC 预览与训练图像采集分别验收。按新部署生成访问配置，不复用历史机器上的隧道地址、认证数据库或过期绝对路径。

### F. 可复用部署与扩容

单机验收后固化 Linux 依赖清单、UE 构建产物、安装/运行脚本；再评估容器和多 worker。起步每卡一路，按 CPU 编码、GPU 渲染、内存与 I/O 实测扩并发。不能根据约 48 GiB 显存直接推断并发倍数。

此前 H800 集群是另一套资源，本方案先迁移到当前 Linux RTX 4090 主机。后续 H800 用于训练或其他已验证的计算阶段；是否参与 UE 渲染需独立验证其图形运行环境，不能复用当前 4090 的结论。

## 8. 实施产物与回退

应交付 Linux 适配代码、可复现的源码/资产清单和依赖版本、机器配置模板、安装/启动/停止入口、GPU 环境检查、systemd 配置、迁移说明、完整数据验证及性能报告。

按阶段推进，先保留 Windows 可用实例和当前验收数据作为对照。Linux 失败时停止该用户所属的任务服务，保留诊断证据；切换只影响明确配置的新部署，不触碰其他主机部署或其他用户进程。
