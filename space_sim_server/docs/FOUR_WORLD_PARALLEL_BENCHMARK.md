# 四实例同时采集验证

使用现有生产 BSK＋MuJoCo＋UE 录制链路，四个独立进程同时运行相同的抽屉任务前 20 秒。每个实例保留两路 1024×1024 相机、主数据 50 Hz、六维力 200 Hz、动力学 400 Hz 单子步。脚本每 200 Hz 更新参考并检查任务，任务的 IK 路径按原有逻辑生成。

本次仅验证四实例的小规模并发和数据完整性；片段到时按现有逻辑写为 total_simulation_timeout，不计为成功完成整个抽屉循环的示范。录制文件单独保存在 run/four-world-benchmark/capture-parallel/episodes。

运行命令（平台 Python，space_sim_server 目录）：

```powershell
python tools/benchmarks/benchmark_parallel_capture.py --mode capture --workers 4 --jobs 4 --seconds 20 --scene run/scenes/scene-20261014-170501-01b5c238.json --output run/four-world-benchmark/capture-parallel --port-base 19760
```

四套实例分别使用 19760–19763、19770–19773、19780–19783、19790–19793；输出目录必须未使用。脚本继续默认双并发，参数现在允许 1–4 并发。进程树内存每秒采样，GPU 每约 5 秒采样，同时记录 UE 进程数和系统可用内存。

历史双并发每批两条约 292.993 秒；比较相同四条数据量时，对应两批约 585.985 秒。历史测试与本次后台负载不同（本次启动前 GPU 使用 396 MiB，历史测试约 3.3 GiB），历史速度只能作为参考，不能当作同批次严格对照。

验收：每路主数据和相机一一对应、主时间间隔 20 ms、力流时间间隔 5 ms、七维 state/action、不同实例会话隔离，以及全部视频帧完整解码。所有测试输出与审计报告留在 run/ 下，不提交录制数据。

全程资源采样：

- 四实例进程树 RSS 峰值 39.61 GiB。
- 系统空闲内存最低 16.50 GiB，四实例运行期间没有耗尽内存。
- 全机 CPU 平均利用率 94.61%，采样峰值 100%。CPU 计算余量已经很小。
- 整张显卡显存占用采样峰值 15,458 MiB（15.10 GiB）；GPU 利用率采样峰值 70%。该显存数包含其他应用，5秒采样不能代表瞬时绝对峰值。

四条数据审计全部通过：每条主流 1001 帧，图像 2002 张，原始六维力 4001 条，均无不完整或拒收样本；主流真实间隔 20 ms，力流 5 ms，七维状态/动作与源 observation 匹配，不同会话彼此隔离。八个视频全部完整解码验证为 1024×1024、50 FPS；八路相机中间帧已目视检查，无黑屏，预览见 camera-preview.png。

限时结束仍保留 failure / total_simulation_timeout 标签。此处“验证通过”指四路采集完整、无串流；不是四条完整抽屉任务成功。

历史双并发按两批完成四条，预计 585.985 秒；本次四并发为 393.101 秒，按该参考数据计算吞吐提高约 49.1%、总时间减少约 32.9%。背景负载、启动和缓存情况不同，此对比仅供参考，未新增同批次双并发对照。

结论：本机当前配置已经实测能同时录制四条，短时数据链路完整。CPU 接近满载；本轮不能证明四实例长时间完整任务的稳定性，也未测试超过四实例。所有本次测试进程已退出，19760–19793 范围内的实验端口无残留监听。
