# 正方形 1K 相机采集

当前平台的所有采集相机（全景 spacecraft_overview、腕部 sarm_wrist_cam）统一输出 1024×1024 RGB，采集仍按 30 Hz 仿真时间采样。新增到同一 RenderComponent 的模型相机沿用相同画布尺寸。

## 配置来源与生效

- `backend/space_arm_platform/camera_defaults.py` 集中定义 Python 默认尺寸；场景清单、后端启动参数、自动录制工具共用。
- PowerShell 平台/后端/场景/渲染启动入口默认也为 1024×1024，回归测试检查它们与清单一致。
- 当前 SARM 模型及生成工具设置同样的尺寸。为保留原水平视野，正方形的垂直视场扩展到全景约 80.593°、腕部约 102.448°；相机位置与朝向不变。
- UE 已有实现按清单创建共享 RGB RenderTarget，并供录制与 Pixel Streaming 使用。此次无需修改或重新编译 C++；已通过真实 UE 验收。
- 停止正在运行的旧场景，重新启动场景后生效。重新启动平台会同时加载新的后台启动默认值。已经录制的数据不转换，也不覆盖。

## 数据格式与尺寸

数据仍为 LeRobot v3，场景控制/渲染/采集协议版本不变。22 个既有特征名和非图像特征定义保持一致。

- 原始 RGB 文件：1024×1024。
- capture 元信息与 Parquet 内 camera_metadata 的 `resolution`：[1024,1024]（宽、高）。
- `meta/info.json` 图像特征 `shape`：[1024,1024,3]（高、宽、通道）。
- MP4：1024×1024、30 FPS；LeRobot 读出的图像张量为 [3,1024,1024]。
- 相机改造本身不改变关节/腕力含义；随后夹爪训练表示已独立升级为 7 维，见 [夹爪训练数据](GRIPPER_TRAINING_REPRESENTATION.md)。源帧号和仿真纳秒时间仍逐帧配对。

写入器继续从真实 RGB 解码尺寸生成特征形状，同时拒绝元信息与图像不一致、同一 episode 中途变更分辨率。历史 640×360 记录仍可读取；新旧图像的 shape 不相同，训练时如混合两种数据，需要统一预处理尺寸。

平台网页原有 object-fit: contain 可正常显示正方形。独立 `C:\Users\LYH\data_display` 查看器已去掉固定 16:9，按实际视频比例显示，并在相机标题显示分辨率。

## 验收

真实 UE + 原权威动力学 + 原采集/LeRobot 链路，5 秒短录制得到 151 帧状态、302 张双相机图像。全部图像、两路 MP4、camera_metadata、特征 shape、视频时间戳、关节/动作/腕力与源观察通过核验。

证据位于 `run/camera-1k-20261015-03/validation.json`；测试 episode 位于该目录的 `episodes/episode-20261015-163739-afc31bed`，标签为 diagnostic/not-demonstration，不混入正式示范数据。

单帧像素数为原 640×360 的约 4.55 倍，会增加渲染、编码、带宽与磁盘开销。30 Hz 指仿真采样频率，不保证墙钟实时 30 帧；此次短录制推进 5 仿真秒约用 16.19 实际秒，不作为其他任务的性能保证。
