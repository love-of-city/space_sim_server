# 2026-10-19 多进程采集与 UE 复用验收

## 改动与部署

新增 `space_sim_server/tools/collect_parallel.py` 和 `config/collection.json`。每路独立端口、种子区间、输出、停止文件与进程树，资源线程数和可选 CPU affinity 从配置加载。每路可以复用 UE，但每条重新创建动力学和录制器。旧单条/串行入口不默认改变行为。

UE 新增 `-BskOfflineCapture`，关闭 WebRTC 相机预览及离屏主视口的无用渲染；保留权威双相机采集。增加 UE/NVENC GPU 序号配置、启动子阶段计时、CPU/内存/GPU 采样、基于通过校验轨迹数的整体吞吐统计。NVENC 没有被设为默认。

修复两项 Linux 连续批量运行问题：`NativePoseProbe` 的 `lms_create` 路径参数在 Linux 需要字节串，而 Windows 保留宽字符；端口预检查在 Linux 允许已关闭连接的 TIME_WAIT，仍拒绝活动监听端口，并通过文件锁协调多个采集调度器。

实际部署路径：`/home/spacesim-zmh/src/space_sim_server`。使用已有 UE 5.6.1 和虚拟环境，无需重新安装引擎。Linux/Windows 插件均增量编译通过。本次没有修改网页场景启停，也没有向远端 Git 推送。

## 小规模实测

Linux 16 vCPU、约 94 GiB RAM、单张 RTX 4090；使用已有模型和着色器缓存。双相机 1024×1024、50 Hz、200 Hz 力数据、compact 存储；CPU H.264 CRF 30 / NVENC QP 30，GOP 2、流式编码。数值相同不代表相同画质。

为比较性能，将关节随机偏移范围设为 0；每条仍使用独立种子及会话。共完成 **8 条 drawer-cycle/5 成功轨迹**，不是大规模随机姿态成功率测试。

| 模式 | 成功条数 | 整批耗时 | 短批次折算吞吐 | 每条正式录制耗时 | 单条大小 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单路 CPU H.264 | 1 | 84.77 s | 42.47 条/小时 | 39.67 s | 26.24 MiB |
| 两路 CPU H.264，每路连续两条 | 4 | 279.05 s | 51.60 条/小时 | 94.32–94.47 s | 26.24–26.26 MiB |
| 单路 NVENC | 1 | 96.93 s | 37.14 条/小时 | 39.12 s | 88.20 MiB |
| 两路 NVENC，每路一条 | 2 | 154.65 s | 46.56 条/小时 | 94.82–94.90 s | 88.06 MiB |

整批耗时包括预检查、进程启动、录制、数据收尾、完整校验和最终退出。各模式条数不同且样本少，不能据此承诺长期稳态倍率。之前 81.2 秒的单条脚本结果不包含同样的批量预检查/全视频校验流程，不能直接比较整体耗时。

单路离线 CPU 录制约 0.87×，此前单条记录约 0.76×；两路同时录制时每路约 0.36×。两路 CPU 的整批吞吐高于本次单路短批次，但不会快两倍。两个 UE 竞争同一卡，GPU 接近满载，暂不建议在此卡上盲目增加至更多路。

## 资源与启动开销

下表为整批采样，包括启动与校验。CPU 是采集进程树之和，100% 为一个逻辑核；RSS 相加可能重复计算共享内存。GPU 为整张卡的系统采样，本次检查没有其他 UE/采集作业。

| 模式 | CPU 平均核等价 | RSS 峰值 | GPU 平均/峰值 |
| --- | ---: | ---: | ---: |
| 单路 CPU | 5.62 | 11.83 GiB | 32.0% / 53% |
| 两路 CPU | 6.93 | 23.04 GiB | 88.0% / 96% |
| 单路 NVENC | 4.63 | 11.86 GiB | 34.1% / 56% |
| 两路 NVENC | 5.67 | 22.96 GiB | 80.9% / 96% |

常驻 UE 的跨会话复用已经通过完整录制验证，但本次没有显著缩短启动关键路径：两路首次启动录制需要约 30.55–30.95 秒，第二条仍需约 31.16–31.25 秒。单条日志显示数据写入器约 2.52 秒就绪，UE 约 11.54 秒可连接，权威动力学首帧约 24.57 秒到达，再固定预热约 5 秒。UE 与动力学本已并行，动力学首帧就绪仍是关键等待点。后续应单独剖析动力学初始化；不能声称复用 UE 已省下整段 31 秒。

预热默认仍为 5 秒，没有通过删掉预热、降低图像分辨率、减少相机、关闭 BSK 或丢帧来提高数字。

## 编码和训练读取

NVENC 降低了 CPU 平均占用，但正式录制时间几乎相同；在当前 QP 30/GOP 2 下体积约为 CPU 版本的 3.36 倍。单路全量校验耗时从 5.62 秒增至 16.42 秒，因此保持 CPU H.264 为默认。

另外用相同的 60 张已解码 RGB 输入做纯编码对比（参考是已有视频解码帧，不是原始无损 UE 图像）：

| 编码 | 编码时间 | 视频字节 | 相对于输入的 RGB PSNR |
| --- | ---: | ---: | ---: |
| CPU H.264 CRF 30 | 0.904 s | 485,093 | 37.35 dB |
| NVENC QP 30 | 0.408 s | 1,056,350 | 41.44 dB |

这说明相同质量数字下 NVENC 输出保留更多信息、也占更多空间。不能把体积差解释成 NVENC 天生压缩率只有三分之一；若以后 CPU 成为瓶颈，应重新匹配码率/画质参数再比较。

8 条轨迹均经过原有 `validate_recording`：任务成功、状态动作维度、数值校验和、200 Hz 力采样、图像/动作配对、两段视频全量解码与时间间隔检查。另用官方 LeRobot/PyAV 读取每条首帧、中帧、尾帧；同一路连续两条具有不同渲染会话号。首帧拼图人工检查可见机械臂、夹爪、任务台与正常材质，无灰棋盘或空画面。
