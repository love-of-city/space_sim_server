# 两个无卡扣活动插头

此实验模板在固定任务盒版本上增加导向插头、航空插头两个独立刚体。上游机械臂、抓夹网格、关节与电机不修改。它不是已完成的整臂插拔任务。

## 模型和碰撞

- 模板 `sarm-task-box-free-plugs`，文件 `model/SARM/platform/sarm_task_box_plugs.xml`。
- `guide_plug`、`aviation_plug` 各有一个自由关节；没有 weld、卡扣、吸附或到位瞬移。
- 插头使用本地 CAD 的实际三角面，保留导向凸起和四个针脚；任务盒对应孔槽仍使用本地 CAD 三角面。
- 固定装配接触掩码从 `0/3` 改为 `0/7`；插头是 `4/7`。新增 bit 4 表示活动插头，因此插头与任务盒、上游 bit 1 机械臂、bit 2 目标可接触。原有机械臂掩码不改。视觉网格继续 `0/0`。
- 原导向存放孔附近的继承凸包封孔，改用其原始表面。右侧接口单元内残留旧任务盒壁的粗碰撞体移除，由本地任务盒 CAD 表面负责该区域；不更改上游源文件。区域选择属于本套 CAD 的配准配置，不是任意 CAD 的通用识别算法。
- 原 CAD 存放姿态存在干涉。实验初始位置保持原 x/y，但导向插头抬高 80 mm、航空插头抬高 65 mm，底端位于台面上方 10 mm。这是明确的试验起点，不能宣称原存放姿态通过装配验收。
- 密度暂取 1000 kg/m³，所得质量约 0.1355/0.0980 kg，仅用于动力学测试；不是实测质量。主卫星原惯量保留，后续仍需统一质量重分配和标定。
- 轨道初始化时两插头继承卫星的轨道位置偏移和速度，防止自由刚体留在世界原点。没有把它们持续固定到卫星。

## 已执行的实物形状测试及边界

`tools/validate_task_box_free_plugs.py` 使用实际插头网格，不再以小球代替插头。先测正确位置、错角度、横向错位，再以 0.03 m/s 初速度做 4 s 自由接近测试；没有每步覆盖插头位姿。

- 导向插头对准后有通路；转错角度时凸起受孔槽阻挡。动态对准测试能到达安装深度。
- 航空插头针脚与针孔接近同径。部分插入阶段无接触，但针脚到达孔口后，对准的动态测试仍停在入口，**尚未完成航空插头插入验收**。没有缩小针脚或放大孔洞来隐藏问题。
- 三角表面接触半径为 10 μm，两相邻表面会产生约 20 μm 数值接触厚度。零间隙配合必须明确区分 CAD 公差、网格离散误差与接触厚度；不能把增大接触柔软度当成正确机械配合。
- 测试退出成功代表配置、阻挡、数值稳定性通过，不代表两个插头均成功插入。报告中的航空插头停止深度是验收问题。

`tools/benchmark_task_box_grip.py` 将**上游原腕部固定在试验台上**，使用原手指和电机、两个插头各测一次。固定腕部改变了引擎默认的父子碰撞过滤，因此测试台显式恢复腕部与手指的原父子排除关系；没有排除手指与插头接触。

每侧手指施加 0.1 N 闭合指令（原电机上限 0.5 N），第三秒给插头施加 0.05 N 轴向外力。稳定测量阶段两侧持续接触，位移约 0.2 mm，无求解警告。没有抓取 weld。此结果证明这组测试条件下能靠接触夹持，**不证明整臂能到达孔口、连续拔插或所有工况下不滑脱**。

## 复现

在仓库根目录，先用带 numpy/scipy/trimesh/rtree 的几何环境执行：

```powershell
python tools/build_task_box_free_plugs.py
```

基础固定模块必须存在且来源校验通过。若 CAD 或上游变化，先按 `TASK_BOX.md` 重建基础模块，再核对自由插头的接口坐标、初始位置和配准。

使用独立 MuJoCo 3.7.0 环境：

```powershell
python tools/validate_task_box_free_plugs.py
python tools/benchmark_task_box_grip.py
```

使用另一个 Basilisk 环境，避免同进程混合 DLL：

```powershell
python tools/benchmark_task_box_native.py --model sarm_ground_target_self_collision.xml
python tools/benchmark_task_box_native.py --model sarm_task_box_module.xml
python tools/benchmark_task_box_native.py --model sarm_task_box_plugs.xml
```

报告在 `reports/task-box-free-plugs.json`、`reports/task-box-grip-load.json`、`reports/native-benchmark-*.json`。运行性能测试时应等待 UE 资产导入和其他重任务结束，采用相同初态多次重复。不要比较不同求解步长、不同控制器或不同硬件负载下的单次时间。

## 平台速度的解释

实时因子 RTF = 仿真前进秒数 / 实际耗时；1 表示跟上实时。离线 MuJoCo、带控制器的原生 MJScene、UE 视频画面是三个不同测量层级。

旧的约 4.1→1.1 秒是开发中的离线物理优化过程，不是完整平台前后延迟。原上游粗碰撞场景缺少新任务盒精细接触，其速度也不能作为等功能的精度对照。

清理顶点降低加载负担；排除固定内部配对、修复假接触、将周边简单实体改为凸体降低碰撞负担。自由插头和针孔接触会重新增加计算量，因此活动模型可能比固定模型慢，不能用固定模型空载速度保证真实插拔实时。

UE 资源使用独立 `TaskBoxPlugs` 目录和 `sarm_task_box_plugs.catalog.json`。网页中选择“本地任务盒（两个活动插头·实验）”；默认上游场景仍保留。当前模型保持 CAD 尺寸，航空针孔配合问题没有自动修正。

## 本机完整平台实测（2026-09-24）

UE 资源导入结束后，分别启动同一份初始姿态配置的三个模板。物理 240 Hz、IK 120 Hz、采集 30 Hz，两路 640×360 相机；启动预热后，各采六个约 5 秒窗口。原始摘要见 [性能结果](results/task-box-platform-performance.json)。

| 模板 | 实际耗时 | 仿真前进 | RTF | 渲染状态发送频率 |
| --- | ---: | ---: | ---: | ---: |
| 上游粗碰撞 | 30.157 s | 20.000 s | 0.663 | 19.90 Hz |
| 固定任务盒精细接触 | 30.187 s | 12.467 s | 0.413 | 12.39 Hz |
| 两个活动插头 | 30.266 s | 13.867 s | 0.458 | 13.74 Hz |

上表为首轮短预热采样，该轮三者均未达到实时。**不能声称任务盒接入让完整平台提速**：它增加了原粗场景没有的精细接触能力。固定版与活动版的一次采样小差异不能作优化因果结论；主机背景负载未完全隔离。本表状态发送频率不是浏览器解码帧率，RTF 不是按键到画面的延迟。

第二轮等待仿真时间达到至少 60 秒，再采六个窗口：

| 模板 | 实际耗时 | 仿真前进 | RTF | 渲染状态发送频率 |
| --- | ---: | ---: | ---: | ---: |
| 上游粗碰撞 | 30.047 s | 31.467 s | 1.047 | 31.42 Hz |
| 固定任务盒精细接触 | 30.187 s | 18.500 s | 0.613 | 18.39 Hz |
| 两个活动插头 | 30.360 s | 10.267 s | 0.338 | 10.14 Hz |

上游超过 1 的窗口包含追赶先前落后时间，不能当作稳定超实时保证。两轮差异明显，不能挑最快一次作为结论。活动插头目前未达到完整平台实时；原先离线优化不能证明平台总体提速。还需隔离背景负载、交替重复和细分 ExecuteSimulation 内部耗时，才能定位可复现的瓶颈。

各组渲染发送队列最多积压 1 帧，主要时间处于 `simulation.ExecuteSimulation()`，其中包含物理、控制和引力计算，尚未进一步拆分归因。不能仅凭这一指标把耗时全部归给碰撞求解。

复现时先在网页启动所需模板，等资源准备完成、预热后，对应日志执行：

```powershell
python tools/record_task_box_runtime.py --log logs/<实例ID>.simulation.out.log --output reports/<模板>-performance.json --windows 6 --warmup-sim-seconds 60
```

工具只采命令启动后新产生的窗口，不混入旧日志。建议交替顺序、多轮重复；不要在资产导入或其他基准测试同时运行时取样。

新模板需要后端加载本次代码后才能出现在列表中。测试结束后恢复原保存场景，从其初始状态重新启动，不恢复测试前的动态状态。
